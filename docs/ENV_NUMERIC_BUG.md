# 数值异常诊断记录（环境级缺陷）

**日期**：2026-11-11  **环境**：Debian 11 / CPython 3.12.16（/usr/local 自编译）/ numpy 2.5.4 / pandas 3.1.1

## 现象

同一份源码在不同调用路径下返回不同结果，且**不抛异常**：

| 表达式 | 期望 | 实际（部分上下文） |
|---|---|---|
| `1.0 / 1.01` | 0.9900990099… | `1.0` |
| `1.0 / 1.5` | 0.6666… | `1.0` |
| `1.0 - 1.0/1.01`（r 来自函数参数） | 0.00990099… | `0.0` |
| `Decimal('1.5') - Decimal(1)`（localcontext 内） | Decimal('0.5') | `Decimal('0')` |
| `Fraction(1) - Fraction(2,3)` → `float(...)` | 0.333… | `0.0` |
| `float(Fraction(1)) - float(Fraction(2,3))` | 0.333… | `0.33333333333333337` |
| `0.1 * 0.2`（经 float 乘） | 0.020000000000000004 | `1.6e30` |
| `math.frexp(1.5)` 尾数 ×2^53（float 乘） | 1.351e16 | `1.351e16` 正常；但 `math.ldexp(3, 100)` 等路径异常 |

## 排查结论

1. **不是我们的代码问题**：从东方财富拉取的原始行情正确（已与官方前复权逐日核对：
   `fqt=1` 返回 5816 位，`fqt=0` 返回 5828 位，成交均价/收盘价之比 ry 正常）。
2. **缺陷在本环境的解释器运行时**：float 四则运算、`float()` 内建、`Decimal`/`Fraction` 转 float 的长尾
   路径、`math.ldexp` 在部分输入下返回错误值。整数运算、`Fraction`/`Decimal` 的内部精确算术
   本身正常，但转回 float 的那一步可能出错。
3. **已排除**：Python 启动文件、`PYTHONPATH` 注入、sitecustomize、numpy 打印选项、缓存字节码
   （逐一验证，见 `tests/test_numguard.py` 的回归用例）。
4. 同一表达式在**不同脚本上下文**结果不同（例如 `python3 -c` 正常、导入包后出错），
   说明缺陷与调用栈/常量池的编译细节相关，属于宿主环境问题，不能靠改写法根除。

## 处置

1. `stellarq.numguard`：集中所有除法/比率/复权/标准化运算，提供自检 `self_test()`；
   启动时**必须**先跑自检，不通过即中止（fail-closed），不允许带着错误数值继续出结论。
2. 每条写进报告的数值都要带「数值自检通过」标记；面板构建时把 `numguard` 自检结果写进
   `run_manifest.json`。
3. 若本环境无法稳定通过自检，量化内核与星图改用**整数/定点**实现或直接在 Node.js
   （v22，ECMAScript 双精度，实测正常）里实现：Node 的 `1/1.01`、`1-1/1.01` 均返回正确值。
4. 该缺陷已实测影响的范围：复权因子（会把整段历史算成 0）、收益率、IC、标准化系数。
   任何在修复前产出的数值结论都应视为**不可用**。

## 复现

```bash
python3 - <<'PY'
print(1.0 - 1.0/1.01)            # 在本环境可能输出 0.0
PY
python3 -c "print(1.0 - 1.0/1.01)"   # 同一表达式在 -c 下正常
PYTHONPATH=src python3 -c "
from stellarq.numguard import self_test
print(self_test()['all_ok'])"
```
